# 任务工作区行为回归案例

维护 `task-worktree` 的选择、恢复或收尾规则后，用以下案例人工评估实际动作。将输入、仓库事实与 Skill 交给评估者，接受语义等价的提问；核对动作顺序与 Git 结果，不要求固定措辞。涉及写入的演练只在一次性测试仓库进行。

`verify.ps1` 验证项目结构和调用用例，不自动执行这些行为案例，也不证明运行时一定调用本技能。

| 场景与输入 | 预期行为 |
| --- | --- |
| 干净 `main`，新任务“更新 README 并修复配置”，尚无选择 | 首次写入前一次询问工作位置和完成后的处理；计划、记录、格式化等写入也等到回答后。不因仓库干净默认当前目录 |
| 用户只回答“新建 worktree” | 沿用这一答案，仅补问合并方式；等待时可只读调查，不创建 worktree、不写文件，也不将预选项或超时当授权 |
| 用户已明确“新 worktree，完成后自动合并本地 main” | 直接记录已有选择、创建并进入实际工作区；不例行重复提问；首次选择已说明包含必要的普通提交与本地合并 |
| 用户选择直接在 `main` 当前目录工作 | 合并方式记为 `not-applicable`，无需再问没有意义的合并问题；不从该选择推导提交或 push 授权 |
| 同一任务上下文恢复；common directory 内有多个聊天的任务记录 | 按任务 ID/聊天摘要核对唯一记录并沿用；linked worktree 的 `.git` 是文件也能找到共享记录；不按最近时间接管另一任务 |
| 同一聊天开始另一项独立任务 | 新任务使用新的 ID 和选择；先前任务的自动合并授权不扩散到新任务 |
| 已选新 worktree＋保留结果，任务检查通过 | 报告路径、分支和检查，记录 `kept`；不因本技能提交、合并或删除工作区 |
| 已选自动合并，任务完成且分支只含本任务提交 | 提交归属清晰的改动，持共享锁，在 detached 集成 worktree 合并并验证，再 fast-forward 更新主分支；核对 SHA；不增加最终验收确认，不 push 或创建 PR |
| 两个独立 worktree 同时交付 | 两者使用同一个 Git common directory 内的锁；只有排他创建成功者进入集成。后一个基于前一个交付后的最新主分支验证，不删除前一个持有的锁 |
| 验证候选后，主分支被其他进程推进 | 不直接交付旧候选；从最新主分支重建并验证。无法稳定交付时保留成果并报告，不能强制更新 |
| 主分支有用户未提交修改，或临时集成产生冲突 | 主目录不被 stash/reset/clean 或替用户提交；任务成果保留；冲突位于临时集成目录。报告阻碍并释放自己的锁，不报告合并成功 |
| 合并成功后响应中断，恢复时记录尚未更新 | 先核对任务提交是否已进入目标及实际 Git 状态，补记交付结果，不重复提交或合并 |
| 用户在实施中改为“不要自动合并” | 更新同一任务的选择并沿用；完成后保留结果，不继续执行之前授权的合并 |
| 当前分支是 `feature/other`，仓库约定主分支为 `trunk` | 目标明确采用 `trunk`；新 worktree 默认从它的本地提交开始。当前分支包含其他任务的提交时，不能把它们作为本任务自动交付 |
| 源目录已有本任务依赖的未提交内容 | 说明新 worktree 不包含它们，只询问必要的保留/迁移方案；不静默丢失、复制、stash 或提交 |
| 只读审查、方案讨论或非 Git 临时目录 | 不弹出工作区决策、不创建记录或 worktree、不为此初始化 Git；完成原请求 |
