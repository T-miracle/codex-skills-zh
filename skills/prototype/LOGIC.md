# 逻辑原型（Logic Prototype）

这是一个微型交互式终端应用，让用户可以手动驱动状态模型。当问题涉及**业务逻辑、状态转换或数据形态（business logic, state transitions, or data shape）**时使用它——这类设计在纸面上看似合理，只有代入真实案例后才会显露问题。

## 何时适合采用这种形式

- “我不确定这个状态机能否处理先发生 X、再发生 Y 的边缘情况。”
- “这个数据模型真的能表示……这种情况吗？”
- “我想在正式编写之前，先亲手感受一下 API 应该是什么样。”
- 任何用户想要**按下按钮并观察状态变化**的场景。

如果问题是“它应该长什么样”，那就选错了分支。请使用 [UI.md](UI.md)。

## 流程（Process）

### 1. 明确问题

编写代码前，先写明要为哪个状态模型、哪个问题制作原型。用一个段落记录在原型 README 中，或写在文件顶部的注释里。回答错误问题的逻辑原型纯属浪费——把问题明确写出，便于之后核对，无论用户此刻正在观看，还是稍后以 AFK 方式回来查看。

### 2. 选择语言

使用宿主项目已有的语言。如果项目没有明显的运行时（例如文档仓库），就询问用户。

遵循项目现有的工具约定——不要仅仅为了原型引入新的包管理器或运行时。

### 3. 把逻辑隔离到可移植模块中

把真正回答问题的逻辑放在一个小型纯接口之后，使它以后可以单独提取并放入真实代码库。外围的 TUI 是一次性的；逻辑模块不应如此。

合适的形式取决于问题：

- **纯 reducer（pure reducer）**——`(state, action) => state`。当操作是离散事件，且状态是单一值时适用。
- **状态机（state machine）**——显式列出状态和转换。当“当前究竟允许哪些操作”也是问题的一部分时适用。
- **作用于普通数据类型的一小组纯函数（pure functions）**。当不存在隐含的当前状态、只有转换过程时适用。
- 当逻辑确实拥有持续存在的内部状态时，使用**方法表面清晰的类或模块**。

选择最符合所问问题的形式，*而不是*最容易接入 TUI 的形式。保持纯净：没有 I/O、没有终端代码、不要用 `console.log` 控制流程。由 TUI 导入并调用逻辑模块；依赖绝不能反向流动。

这正是原型在生命周期结束后仍有价值的原因：问题得到回答后，验证过的 reducer／状态机／函数集可以独立提取到真实模块中。

### 4. 构建能呈现状态的最小 TUI

把它构建为**轻量 TUI（lightweight TUI）**——每次刷新时清屏（`console.clear()` / `print("\033[2J\033[H")` / 等效方式），然后重新渲染完整画面。用户应始终看到一个稳定视图，而不是不断增长的回滚记录。

每一帧按以下顺序包含两部分：

1. **当前状态（Current state）**：以美观且便于比较差异的形式打印（每行一个字段，或格式化 JSON）。字段名或小节标题使用**粗体（bold）**，不太重要的上下文（时间戳、ID、派生值）使用**暗淡样式（dim）**。可以直接使用原生 ANSI 转义码——`\x1b[1m` 表示粗体，`\x1b[2m` 表示暗淡，`\x1b[0m` 表示重置。除非项目中已有样式库，否则无需额外引入。
2. **键盘快捷键（Keyboard shortcuts）**：列在底部：`[a] add user  [d] delete user  [t] tick clock  [q] quit`。可以让按键加粗、说明变暗，也可以反过来——以清晰易读为准。

行为（Behaviour）：

1. **初始化状态（Initialise state）**——使用单个内存对象／结构体。启动时渲染第一帧。
2. 每次**读取一个按键（或一行）**，再分派给修改状态的处理器。
3. 每次操作后**重新渲染（Re-render）**完整画面——不要追加，而要替换。
4. **循环直到退出。**

整个画面应能容纳在一屏内。

### 5. 确保一条命令即可运行

在项目现有的任务运行器中添加脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户只需运行 `pnpm run <prototype-name>` 或等效命令——绝不应该需要记住路径。

如果宿主项目没有任务运行器，就把命令放在原型 README 顶部。

### 6. 交给用户

把运行命令交给用户，让他们亲自驱动。最有价值的时刻，是他们说出“等等，这不应该发生”或“咦，我原以为 X 会不一样”——这些是_想法_本身的缺陷，而发现它们正是原型的目的。如果用户希望添加新操作，就添加；原型会不断演进。

### 7. 保存答案与原型

原型回答问题后，先保存答案，再按 [SKILL](SKILL.md) 所述方式保存原型。对逻辑原型而言，映射关系如下：将验证过的 reducer／状态机／函数集提取到真实模块中（决策被吸收）；TUI 外壳则随一次性分支保留，把原型作为一手资料保存。

## 反模式（Anti-patterns）

- **不要添加测试。** 需要测试的原型已经不再是原型。
- **不要连接真实数据库。** 除非问题专门涉及持久化，否则使用内存存储。
- **不要泛化。** 不要考虑“如果以后想支持 X 怎么办”。原型只回答一个问题。
- **不要把逻辑和 TUI 混在一起。** 如果 reducer／状态机引用了 `console.log`、提示符或终端转义码，它就不再可移植。让 TUI 只作为纯模块之上的薄外壳。
- **不要把 TUI 外壳交付到生产环境。** 外壳针对从终端手动驱动进行了优化；真正值得保留的是它后面的逻辑模块。
