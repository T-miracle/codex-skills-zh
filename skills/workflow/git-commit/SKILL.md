# Git 提交

以实际变更为依据，产出可独立理解、可回退的原子提交（atomic commit）。按请求选择写信息、检查信息或执行提交；自动调用本技能本身不代表获得提交授权。

## 1. 确定规范与范围

- 优先采用用户指定规则和仓库的 `AGENTS.md`、`CONTRIBUTING`、提交模板及 commitlint 配置；没有约定时使用下方默认格式。
- 编写信息前先确定项目主要自然语言（例如中文或英文）：用户明确指定的提交语言优先，其次是仓库明确约定；否则查看近期人工提交（可从 `git log -20 --format=%s` 开始），结合主 README、贡献文档及维护者注释推断。排除机器人提交、生成内容和翻译副本的干扰，不以代码标识符、机器时区或用户所在地判断项目语言。证据混杂时优先延续近期人工提交的主流语言；仍无依据时采用用户当前交流语言，并简短说明这一假设。
- 仅咨询格式或提供了充分的变更描述时，直接据此回答，不要求 Git 工作区。根据描述生成的草稿应说明依据，不能声称已验证代码。
- 对当前仓库生成或执行提交时，读取 `git status --short`、`git diff --cached`、`git diff`；逐个检查范围内未跟踪文件。用户指定“已暂存”时，以 index 内容为提交事实，即使同一文件还有未暂存修改。
- 按下面的分组规则确定每项逻辑修改的归属，再选择 type；文件、工单和 type 都不是提交边界。

### 分组规则

- **功能按交付目的合并**：尚未提交的新功能，其后续补充、开发中相关 BUG 修复、配套测试和文档归为一个 `feat` 提交。已经提交的功能，后续修复另建 `fix`；仅在明确授权整理未共享历史时考虑合回原提交。
- **修复按根因合并**：同一根因且同一修复解决的多个 BUG 放入一个 `fix`，说明影响并包含回归测试。不同根因、可独立修复的 BUG 分开；开发新功能时顺手修复的独立旧缺陷也单独提交。
- **配套改动按必要性归属**：去掉该修改，功能是否仍能正确交付？必需的重构、依赖升级、测试和使用说明随功能；有独立价值的公共前置改动可先提交。顺手清理、无关格式化、独立升级和文档修正按各自目的分组，不能因同属 `chore` 合并。
- **提交按依赖排序**：每一步都应形成可构建、可验证的完整状态。共享改动有独立意义时先提交；否则放入首先需要它的功能提交，后续提交依赖前者。

涉及多个目的、同文件拆分或部分暂存时，在确定分组前读取 [拆分与验证](references/splitting-commits.md)，执行时沿用该参考。

完成标准：规范、证据来源和操作模式已确定；范围内每项逻辑修改恰有一个归属，提交顺序满足依赖。拆分明确且已有提交授权时直接执行、完成后汇报；只有归属或范围存在实质歧义时，先展示推荐方案（目的、逻辑修改、依赖和验证方式），等待用户确认后再执行相关提交。技术上难拆时先按参考处理，不据此反复索要确认。

## 2. 编写或检查信息

默认格式如下，scope、`!`、body 和 footer 均按实际需要选用：

```text
<type>(<scope>)!: <subject>

<body>

<footer>
```

| type | 默认选择依据 |
| --- | --- |
| `feat` | 增加使用者可用的功能 |
| `fix` | 修正错误行为 |
| `docs` | 仅文档或说明性注释 |
| `style` | 仅空格、缩进等代码格式；视觉样式变化按功能或修复意图判断 |
| `refactor` | 改变实现结构，保持外部行为 |
| `perf` | 性能改进 |
| `test` | 独立的测试变更 |
| `build` | 构建系统或依赖变更 |
| `ci` | 持续集成配置 |
| `chore` | 未被以上覆盖的维护；仅版本变更采用 `chore(release)` |
| `revert` | 撤销变更，正文注明实际被撤销的提交及原因 |

这些扩展类型是默认团队约定，Conventional Commits 并未强制一份完整类型枚举。

- scope 取稳定的模块或领域名；跨模块且没有合适范围时省略。subject 说明具体变化，避免“更新代码”等无信息概括。
- subject、body 和 footer 的自然语言说明使用第 1 步确定的语言；`feat`、`fix`、`BREAKING CHANGE` 等协议词、既有 scope、代码标识符和专有名词保留原文。版本提交中的示例描述也按此规则调整。标题长度服从仓库规则，无规定时保持简洁，不把固定字符数当成规范硬要求。
- body 按需解释原因和行为影响；footer 只引用真实且与任务有关的 Issue。无法确认关闭意图时使用关联说明，不虚构 `Closes`。
- 判断兼容性，而非改动行数。存在破坏性变更时使用 `!` 或 `BREAKING CHANGE:`；推荐在 footer 写明受影响契约及迁移方式。`refactor`、`chore` 等类型同样可能含破坏性变更。
- 检查已有信息时分别判断语法与语义：格式合法仍可能类型错误、遗漏破坏性影响或与 diff 不符。指出具体偏差并给出修订稿。

完成标准：每组变更都有与证据一致的信息，描述语言与项目证据或明确指定一致，兼容性影响已评估，仓库格式约束已应用。仅请求信息或检查时在此交付，不进入执行分支。

## 3. 按授权执行并核对

用户明确要求“提交这些改动”等即授权对应范围的普通提交；已有授权继续有效。“写提交信息”“看看怎么提交”只产出草稿。amend、历史重写、tag、push 和发布分别按用户实际授权执行，不能从普通 commit 请求推导。

涉及版本文件、`npm version` 或已有版本提交时，先读取 [版本提交](references/version-commits.md)。

执行普通提交时：

1. 检查现有 index 是否包含范围外内容；只暂存目标文件或 hunks。若混入他人已暂存内容，先明确处理方案，保留其暂存状态和工作区修改。不要以 `git add .` 或 `git commit -a` 代替范围选择。
2. 复核最终 `git diff --cached` 和 `git diff --cached --check`；空 diff 时报告无可提交内容。运行仓库要求且与变更相关的检查，验证对象是“此前提交＋本次 index”。工作区含其他修改时，按 [拆分与验证](references/splitting-commits.md) 隔离检查；已有检查仅在对应相同内容与环境时复用。
3. 用 `git commit -F <message-file>` 提交审阅后的信息；消息文件放在仓库外的临时目录，保留真实换行并使用 UTF-8。按当前 shell 正确传递参数，不把消息正文拼成可执行命令。
4. hook 失败时检查原因及其修改，修复范围内问题后重新审阅；禁止为通过提交擅自使用 `--no-verify`。命令失败或结果不确定时先检查 HEAD、index 和工作区，确认是否已经生成提交，再决定下一步。
5. 用 `git log -1 --format=fuller`、`git show --stat --oneline HEAD` 和 `git status --short` 核对结果。拆分多次提交时逐次重复核对，避免重复提交或遗漏变更。

完成标准：报告实际提交的哈希、信息和检查结果，以及仍未提交的相关内容；未执行时明确交付的是草稿。执行被阻止时说明具体原因，不报告成功。
