# 拆分与验证

## 按逻辑修改暂存

依据主流程已确定的目的分组。同一文件可进入多个提交：逐个选择或编辑 hunk，只暂存属于本次目的的修改行；一个 hunk 也可能包含多个目的。每次检查完整暂存 diff，确认上下文和必要依赖齐全。

修改重叠在同一行或代码段时，先构造各自完整的中间版本，再形成逐次提交的内容。优先在隔离副本或临时 index 中准备这些版本，保留原工作区和原暂存状态；不要靠删除未提交内容来腾出拆分空间。

如果拆分必须引入仅为过渡服务的临时代码，或无法得到独立可验证的中间状态，可将耦合部分合为最小完整提交，并在结果中说明原因。仅属于同文件、同行或同 hunk 不构成合并理由。

完成标准：本次暂存只包含对应逻辑修改及必需依赖；其余修改仍可用于后续提交，范围外内容及原有暂存状态被保留。

## 验证每一步实际状态

对代码提交，在隔离目录中构造“此前提交＋本次 index”的完整文件树，并运行相关构建或测试。使用能够保留项目所需文件模式、符号链接等语义的导出方式；项目依赖与生成过程遵循仓库约定，不把含后续修改的源文件或构建产物混入验证环境。

验证至少覆盖暂存修改的行为和必要依赖。文档、格式等低影响提交使用对应检查；只有仓库要求或影响范围需要时才运行完整测试。检查结果记录对应的候选内容；暂存内容被 hook 或后续修改改变时，重新审阅并补做受影响的检查。

若无法隔离验证，说明具体缺失条件及已完成的检查。整个工作区测试通过不能代替本次提交通过；仓库必需检查未满足时，遵循其门禁，不把说明限制当作豁免。

完成标准：每次提交都有与实际候选状态对应的检查结果，或明确的验证限制；没有借用后续未提交修改使当前提交通过。

## 核对完整序列

拆分前保留目标文件最终内容的可核对快照，包括新增、删除及文件模式变化。全部提交完成后，逐项比较最终状态，确认拆分没有改变原本要交付的内容，没有漏项或重复纳入；范围外修改及其暂存状态仍与拆分前一致。

若检查或 hook 引入实际修正，单独核对其归属和影响，以经审阅的修正更新预期；不能以“保持原内容”为由撤销必要修复，也不能把无关改动悄悄带入。

完成标准：每项目标修改已在提交序列中落实，最终内容与经审阅的预期一致；汇报各提交及相关剩余内容，必要时说明耦合合并理由和验证限制。
