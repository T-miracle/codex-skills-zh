# 编写与维护前端代码注释

把注释视为代码契约的一部分：先从类型、调用点、测试和已确认接口中取得事实，再用最短且可维护的文字解释代码无法自行表达的语义。不得为了满足“有注释”而复述语法、猜测业务或保留已经过时的说明。

## 与其他 Skill 协作

- 本 Skill 可单独执行，也可由 `$writing-vue-components`、`$organizing-frontend-components`、`$integrating-frontend-apis` 或其他实现类 Skill 在代码生成后、验证前调用。
- 调用方传入目标文件或本轮 diff；本 Skill 只处理该范围及为保持注释准确所必需的直接关联代码，不擅自给整个仓库补注释。
- 注释完成后把控制权交还调用方继续 formatter、lint、typecheck、测试和构建。
- 当前只覆盖浏览器前端的 JavaScript、TypeScript、Vue、React 及其测试、模型、composable/hook、API adapter；其他语言留待后续扩展。

## 1. 建立注释契约

先读取仓库指令、目标文件、相邻代码、格式化与 lint 配置，并检查是否已经使用 JSDoc、TSDoc、TypeDoc、ESLint JSDoc 规则或框架专用写法。确定：

- 项目是 JavaScript 还是 TypeScript；Vue/React 版本与 API 风格；
- 现有注释语言、标点、标签顺序和导出 API 的详细程度；
- 本轮新增或修改了哪些函数、方法、class、实体字段与复杂流程；
- 参数、返回值、字段单位、可空性、副作用、异常和接口字段分别有什么证据。

证据优先级为：已确认契约或类型定义、可执行测试、真实调用点、同模块稳定约定。不得从名称或相似页面猜测字段含义、单位、接口行为或异常条件。若事实仍未知，只能在代码本身已经是显式 Mock/TODO 时标注“契约待确认”；否则先报告缺失事实，不写伪精确注释。

完成标准：注释语言与格式已确定；所有必须注释的目标已列出；每项说明都能追溯到代码或契约证据。

## 2. 为新增代码生成注释

以下新增声明必须在同一次变更中获得文档注释：

- 具名函数、赋给标识符的函数、组件方法、class method、computed getter、hook/composable；
- class、实体类、表单模型、视图模型以及它们的字段；
- 导出的工具函数、API adapter、类型守卫和包含业务语义的事件处理器。

函数注释必须说明用途、每个参数和返回值；异步函数说明 resolve 的值，`void` 函数也明确无返回值。构造函数不写返回值。存在副作用、抛错、前置条件、单位或边界行为时再补相应说明。短小匿名内联回调（如 `items.map(item => item.id)`）不单独写文档块；一旦回调承载业务规则或多阶段逻辑，应提取为具名函数并注释。

实体或模型 class 必须说明职责；每个字段都要让读者在声明附近看到类型、业务含义及必要备注，例如单位、取值范围、缺省值、是否由接口回填。JavaScript 用 JSDoc 标签承载类型；TypeScript 仍以类型声明为单一事实来源，但按本地规则在字段注释中写出与声明一致的可读类型备注，并在类型变化时同步更新。详细写法与示例见 [前端注释规则](references/comment-rules.md)。

完成标准：所有新增目标都有准确注释；函数参数与返回值完整；实体字段的类型和含义均可直接定位；没有为了凑数量而产生的逐行翻译式注释。

## 3. 补充复杂流程注释

只在代码结构仍不足以表达意图时添加块前注释，优先解释：

- 为什么必须采用这个顺序、分支或兼容处理；
- 跨 API、表单、缓存或组件状态的阶段边界；
- 不变量、竞态规避、回滚条件、非显然的性能取舍；
- 外部组件库或浏览器行为造成的限制。

注释放在所解释代码之前，描述约束和目的，不逐行翻译“赋值、判断、循环”。若一段流程需要大量注释才能理解，先考虑提取具名函数、缩短分支或建立清晰的数据边界，再对剩余的非显然原因做说明。

完成标准：复杂点有“为什么”的解释；简单代码没有噪声注释；被注释的流程边界与实际执行顺序一致。

## 4. 同步修改代码的注释

检查本轮 diff 邻近的已有文档块和流程注释。若参数、返回值、字段类型或语义、副作用、异常、顺序、不变量、默认值、API 映射发生变化，必须在同一变更中更新或重写注释。仅有格式、变量改名或内部实现微调，且原注释仍完全准确时，可以保持不变。

删除已经失真的说明、被注释掉的旧代码和无负责人或退出条件的陈旧 TODO。不要借机大范围改写无关注释；若发现范围外的错误注释，在交付中单独指出。

完成标准：代码和注释描述同一份当前契约；本轮修改没有留下过时参数名、返回值、字段说明或流程步骤。

## 5. 格式化与验证

对全部受影响文件运行项目原生 formatter，并按项目能力运行 lint、typecheck、相关测试与文档生成检查。若仓库配置了 ESLint JSDoc、TypeDoc 或 TSDoc 校验，必须通过；若未配置，不擅自添加依赖。

最后逐项复查：

1. 新增函数、方法、class 和实体字段是否都已覆盖；
2. 参数名与签名是否逐一对应，返回值是否准确；
3. JavaScript 类型是否由 JSDoc 表达，TypeScript 字段的类型备注是否与权威声明一致；
4. 修改后的注释是否仍与行为一致；
5. 是否存在猜测、复述代码、无效 TODO 或被注释掉的旧实现；
6. formatter 与所有适用检查是否通过。

完成标准：注释覆盖门禁通过，格式化和适用检查已执行；未运行项说明具体原因，当前范围内可修复的问题已修复并重新验证。

需要扩展或审查本规范本身时，再读取 [标准调研记录](references/standards-research.md)。
