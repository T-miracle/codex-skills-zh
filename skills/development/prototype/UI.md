# UI 原型（UI Prototype）

在单一路由上生成**多个截然不同的 UI 变体**，并通过底部悬浮栏切换。用户在浏览器中来回查看各个变体，选出一个（或从每个变体中抽取部分元素），再丢弃其余方案。

如果问题涉及逻辑／状态，而不是某个东西应该长什么样，那就选错了分支。请使用 [LOGIC.md](LOGIC.md)。

## 何时适合采用这种形式

- “这个页面应该长什么样？”
- “我想先看看这个仪表盘的几个方案，再作决定。”
- “为设置界面尝试一种不同的布局。”
- 任何用户原本需要花一整天，在脑海中三个模糊模型之间犹豫的场景。

## 两种子形式——强烈优先选择子形式 A

当 UI 原型**紧贴应用其余部分**时，更容易判断优劣——真实页眉、真实侧边栏、真实数据、真实信息密度。单独的一次性路由如同真空环境：每个变体孤立看起来都不错。只要现有页面有可能承载这些变体，就默认选择子形式 A。只有原型确实无处安放时，才使用子形式 B。

### 子形式 A——调整现有页面（首选）

路由已经存在。各个变体**在同一路由上**渲染，并由 `?variant=` URL 查询参数控制。保留现有的数据获取、参数和身份验证——只切换渲染内容。这是默认选择；除非有具体理由，否则就用它。

如果原型对应的内容还没有页面，但*自然应该存在于某个页面内部*（仪表盘的新区域、设置界面的新卡片、现有流程的新步骤），它仍属于子形式 A。把变体挂载到宿主页面内。

### 子形式 B——新页面（最后手段）

只有原型内容确实没有任何现有页面可以容纳时才使用——例如全新的顶级界面，或无法合理嵌入任何位置的流程。

按照项目已有的路由约定创建一条**一次性路由（throwaway route）**——不要发明新的顶层结构。命名应明确表明它是原型（例如在路径或文件名中包含 `prototype`）。同样使用 `?variant=` 模式。

决定采用子形式 B 前，先做合理性检查：真的没有任何现有页面可以嵌入它吗？空白路由会掩盖那些在内容充实的页面上才会暴露的设计问题。

两种子形式使用完全相同的底部悬浮栏。

## 流程（Process）

### 1. 明确问题并选择数量 N

默认生成**3 个变体**。超过 5 个后，方案不再是截然不同，而会开始形成噪声——上限设为 5。

在原型所在位置或文件顶部注释中，用一行写下计划：

> "Three variants of the settings page, switchable via `?variant=`, on the existing `/settings` route."

无论用户是否正在场、能否立即提出异议，这种方式都有效。

### 2. 生成截然不同的变体

起草每个变体，并确保各自遵守：

- 页面用途及其可访问的数据。
- 项目的组件库／样式系统（TailwindCSS、shadcn、MUI、纯 CSS 或其他系统）。
- 清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

各变体必须在**结构上不同（structurally different）**——布局不同、信息层次不同、主要交互暗示不同，而不只是颜色不同。三个稍作调整的卡片网格不是 UI 原型，只是壁纸。如果两个草案太相似，明确要求“不要使用卡片网格”，然后重做其中一个。

### 3. 把它们连接起来

在路由上创建单个切换器组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形式 A（现有页面）：把所有现有数据获取逻辑保留在切换器上方；每个变体只改变渲染的子树。

对于子形式 B（新页面）：让 `/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

在屏幕底部中央放置一个小型固定定位栏，其中包含三部分：

- **左箭头（Left arrow）**——循环切换到上一个变体。
- **变体标签（Variant label）**——显示当前变体键；如果变体导出了名称，也一并显示。例如 `B — Sidebar layout`。
- **右箭头（Right arrow）**——循环切换到下一个变体。

行为（Behaviour）：

- 单击箭头时更新 URL 查询参数（使用框架路由器——Next 使用 `router.replace`，React Router 使用 `navigate`，等等），使变体链接可以共享，并在重新加载后保持稳定。
- 键盘：`←` 和 `→` 方向键也可循环切换。当焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 上时，不要拦截方向键。
- 在视觉上与页面明确区分（例如高对比度胶囊形状、轻微阴影），使人一眼看出它不属于正在评估的设计。
- 在生产构建中隐藏——使用 `process.env.NODE_ENV !== 'production'` 或等效检查作为门禁，防止意外合并原型后把切换栏交付给用户。

把切换器放入单个共享组件，使两种子形式都能复用。将其置于项目存放共享 UI 的位置。

### 5. 交给用户

提供 URL（以及各个 `?variant=` 键）。用户有空时会自行浏览。最有价值的反馈通常是**“我想要 B 的页眉，再搭配 C 的侧边栏”**——这才是他们真正想要的设计。

### 6. 保存答案并清理

确定胜出变体后，先记录答案——哪个变体胜出及其原因——再按 [SKILL](SKILL.md) 所述方式保存原型。把胜出方案整合进真实代码，其余内容移到一次性分支，而不是主分支：

- **子形式 A**——把胜出方案整合进现有页面；从主分支移除落选变体和切换器。
- **子形式 B**——把胜出变体提升为真实路由；从主分支移除一次性路由和切换器。

完整变体集合是一手资料，因此应保存在一次性分支，而不是垃圾桶——遗留在主分支中的变体组件和切换器很快就会腐化，并迷惑下一位读者。

## 反模式（Anti-patterns）

- **变体只在颜色或文案上不同。** 那只是微调，不是原型。真正的变体会在结构上持不同意见。
- **变体之间共享过多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 则违背原型目的。每个变体都应能自由抛弃现有布局。
- **把变体连接到真实写操作。** 只读原型没有问题。如果变体需要修改数据，把它指向 stub——要回答的问题是“它应该长什么样”，不是“后端能否工作”。
- **直接把原型提升到生产环境。** 变体代码是在原型约束下编写的（无测试、错误处理最少）。整合时应按生产标准重新编写。
