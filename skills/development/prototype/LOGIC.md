# 逻辑原型（Logic Prototype）

用一个独立、完整的 HTML 文件构建**可分享演示（shareable demo）**，让任何人都能点击按钮来操作状态模型。当问题涉及**业务逻辑、状态转换或数据形状（business logic, state transitions, or data shape）**时使用：这些内容在纸面上看似合理，经过真实案例才会显露问题。

它只有一个文件，不需要安装，可交给设计师、产品经理或领域专家，让非开发者亲自感受模型。因此，应使用他们的语言，而非代码语言。

## 适用情形（When this is the right shape）

- “我不确定这个状态机能否处理先发生 X、再发生 Y 的边界情况。”
- “这个数据模型真的能表达这样的情况吗……”
- “写代码之前，我想先体验一下 API 应该是什么样。”
- 任何需要**点击按钮并观察状态变化（press buttons and watch state change）**的情况。

如果问题是“它应该长什么样”，应使用 [UI.md](UI.md)。

## 流程（Process）

### 1. 明确问题

编写代码前，先写下要验证的状态模型和问题。在演示顶部用一段可见说明表达，不要只放在注释中。回答错误问题的逻辑原型毫无价值，所以问题必须明确，方便用户当场检查，或离席（AFK）后回来核对。

### 2. 把逻辑隔离为可移植模块

把实际回答问题的逻辑放在一个 `<script>` 块中，写成可直接提取到真实代码库的小型纯模块。外围页面是一次性的，逻辑模块不是。

形状取决于问题：

- **纯 reducer（pure reducer）**：`(state, action) => state`。适用于离散动作事件和单一状态值。
- **状态机（state machine）**：显式状态与转换。适用于“当前哪些动作合法”本身就是问题的情况。
- **作用于普通数据类型的一小组纯函数（A small set of pure functions）**。适用于没有隐式当前状态、只有转换的情况。
- **拥有清晰方法接口的类或模块（A class or module with a clear method surface）**。适用于逻辑确实持有持续内部状态的情况。

选择最符合问题的形状，*而不是（not）*最容易接到页面的形状。保持逻辑纯粹：不访问 DOM、`document`，按钮处理器也不深入其内部。页面调用模块，模块不反向依赖页面。这让原型在完成问题后仍然有用：经过验证的 reducer、状态机或函数组可以独立移入真实模块。

### 3. 构建可分享的 HTML 文件

单文件，普通 HTML/CSS/JS，全部内联，无框架、打包器或服务器，双击即可打开，也能通过邮件分享。任何人都应能通过打开文件运行。

面向非开发者编写。每个标签都用**领域语言（domain language）**：按钮与状态描述业务，而不是 reducer。用普通话语解释正在发生什么。

从上到下采用清晰层级：

1. **标题和一句话说明（Title and one-line explanation）**：说明演示可探索什么，即第 1 步的问题。
2. **当前状态（Current state）**：完整相关状态显示在可读面板中，使用有标签的字段，而非原始 JSON。每次点击后重新渲染，让变化可见；有助于非开发者理解时，标出刚刚改变的部分。
3. **自由探索按钮（Free-play buttons）**：每个动作一个按钮，始终可用，让用户按任意顺序试探模型。每次点击派发动作并重新渲染状态。
4. **引导式演练（Guided walkthroughs）**：一组**场景（scenarios）**，每个标签页一个。每页用简短普通语言说明场景、初始情况和观察重点，下面依次列出该场景**需要点击的按钮（buttons to press）**。每一步都是真按钮：点击即执行动作并推进一步。启动演练时重置到已知初始状态，确保每次运行一致。

选择能展示纸面上难以推理的案例：正常路径、棘手边界情况，以及一次本应非法的操作。

保持美观、克制：清晰排版、宽松间距、一种强调色。避免动画和花哨效果，让状态与按钮成为焦点。

### 4. 交给用户

把文件交给用户，或为他们打开。用户有空时可运行演练并自由探索。“等等，这不应该发生”或“我以为 X 会不同”的时刻最有价值：它们揭示_想法（idea）_中的缺陷，这正是目的。如果需要新动作或新场景，就继续添加，原型可以演进。

### 5. 记录答案与原型

原型回答问题后，记录答案，再按 [SKILL](SKILL.md) 的说明保留原型。逻辑原型的具体对应关系是：经过验证的 reducer、状态机或函数组移入真实模块，决策随之被吸收；HTML 外壳随原型留在一次性分支上，作为一手来源。它只有一个独立文件，因此在该分支上仍可轻松再次运行。

## 反模式（Anti-patterns）

- **不要添加测试（Don't add tests）。**需要测试的原型已经不再是原型。
- **不要接入真实数据库（Don't wire it to the real database）。**除非问题明确涉及持久化，否则使用内存状态。
- **不要泛化（Don't generalise）。**不考虑“以后还想支持 X”；原型只回答一个问题。
- **不要混合逻辑与页面（Don't blur the logic and the page together）。**纯模块一旦引用 DOM、`document` 或按钮处理器，就无法独立提取。让页面只是纯模块上的薄外壳。
- **不要引入框架、打包器或服务器（Don't reach for a framework, bundler, or server）。**交付用户双击即可运行的一个文件；React 应用或开发服务器会破坏可分享性。
- **不要把 HTML 外壳发布到生产环境（Don't ship the HTML shell into production）。**页面为人工点击探索而优化，后面的逻辑模块才值得保留。
