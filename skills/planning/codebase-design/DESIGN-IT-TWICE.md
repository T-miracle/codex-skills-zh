# 设计两次（Design It Twice）

当用户希望为选定的深化候选项探索替代接口时，使用这种并行子代理（parallel sub-agent）模式。它基于 Ousterhout 的“Design It Twice”原则——你的第一个想法不太可能是最佳方案。

本文使用 [SKILL.md](SKILL.md) 中的词汇——**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**、**杠杆率（leverage）**。

## 流程（Process）

### 1. 界定问题空间

生成子代理之前，先面向用户说明所选候选项的问题空间：

- 任何新接口都必须满足的约束
- 它所依赖的对象及其所属类别（参见 [DEEPENING.md](DEEPENING.md)）
- 一份粗略的说明性代码草图，用来让约束落地——它不是提案，只是把约束具体化的方法

向用户展示这些内容，然后立即进入步骤 2。用户阅读和思考的同时，子代理并行工作。

### 2. 生成子代理

使用 Agent 工具并行生成至少 3 个子代理。每个子代理都必须为深化模块产出一个**截然不同**的接口。

为每个子代理提供独立的技术简报（文件路径、耦合细节、[DEEPENING.md](DEEPENING.md) 中的依赖类别、接缝后隐藏的内容）。该简报独立于步骤 1 面向用户的问题空间说明。为每个代理指定不同的设计约束：

- 代理 1：“最小化接口——最多设置 1–3 个入口点。最大化每个入口点的杠杆率。”
- 代理 2：“最大化灵活性——支持多种用例和扩展。”
- 代理 3：“针对最常见调用者优化——让默认场景极其简单。”
- 代理 4（如适用）：“围绕端口与适配器设计跨接缝依赖。”

简报中同时包含 [SKILL.md](SKILL.md) 词汇和 CONTEXT.md 词汇，使每个子代理的命名同时符合架构语言和项目领域语言。

每个子代理输出：

1. 接口（类型、方法、参数——以及不变量、顺序、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现在接缝后隐藏了什么
4. 依赖策略和适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——哪些位置杠杆率高，哪些位置较低

### 3. 展示并比较

依次展示各个设计，让用户逐一消化，再用文字进行比较。比较维度包括**深度（depth）**（接口处的杠杆率）、**局部性（locality）**（变更集中在哪里）以及**接缝位置（seam placement）**。

比较后给出你自己的建议：你认为哪个设计最强，以及原因。如果不同设计中的元素适合组合，提出混合方案。要有明确立场——用户需要的是有力判断，而不是菜单。
