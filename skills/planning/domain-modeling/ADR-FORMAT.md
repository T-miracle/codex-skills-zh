# ADR 格式

ADR 存放在 `docs/adr/` 中，并使用连续编号：`0001-slug.md`、`0002-slug.md`，依此类推。

按需创建 `docs/adr/` 目录——只在需要第一份 ADR 时创建。

## 模板（Template）

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

仅此而已。一份 ADR 可以只有一个段落。它的价值在于记录*已经做出决策*以及*为何这样决定*，而不是填满各个小节。

## 可选小节

只有在确实能增加价值时才包含以下内容。大多数 ADR 都不需要它们。

- **状态（Status）**前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——重新审视决策时很有用
- **考虑过的选项（Considered Options）**——只有被拒绝的替代方案值得记住时才加入
- **后果（Consequences）**——只有需要指出不明显的下游影响时才加入

## 编号（Numbering）

扫描 `docs/adr/` 中现有的最大编号，再加一。

## 何时建议编写 ADR

以下三个条件必须全部成立：

1. **难以逆转（Hard to reverse）**——日后改变决定会产生显著成本
2. **缺少上下文就显得意外（Surprising without context）**——未来读者看到代码会疑惑：“他们究竟为什么要这样做？”
3. **真实权衡的结果（The result of a real trade-off）**——确实存在替代方案，而你出于具体原因选择了其中一个

如果决策容易逆转，就跳过——需要时直接逆转即可。如果它毫不意外，就没人会追问原因。如果本来就没有真正的替代方案，那么除了“我们选择了显而易见的做法”，也没什么值得记录。

### 哪些决策符合条件

- **架构形态。** “我们使用 monorepo。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。”
- **带来锁定效应的技术选择。** 数据库、消息总线、身份验证提供商、部署目标。不是每个库都要记录——只记录那些更换需要一个季度的选择。
- **边界与范围决策。** “客户数据由 Customer 上下文拥有；其他上下文只能通过 ID 引用。”明确的“不做什么”与“做什么”同样有价值。
- **有意偏离显而易见的路径。** “因为 X，我们使用手写 SQL 而不是 ORM。”凡是理性读者可能默认采用相反做法的情况都属于此类。这能阻止下一位工程师把刻意设计“修正”掉。
- **代码中不可见的约束。** “由于合规要求，我们不能使用 AWS。”“因为合作方 API 合同，响应时间必须低于 200ms。”
- **拒绝理由并不明显的替代方案。** 如果你考虑过 GraphQL，却出于微妙原因选择 REST，请记录下来——否则六个月后还会有人再次建议 GraphQL。
