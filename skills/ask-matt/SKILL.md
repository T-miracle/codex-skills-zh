# 询问 Matt（Ask Matt）

你不可能记住每个技能，所以直接询问。

**流程（flow）** 是一条穿过各项技能的路径。大多数路径沿一条 **主流程（main flow）** 前进，并有两条 **入口支线（on-ramps）** 汇入其中。其他技能要么独立运行，要么作为底层词汇层提供支持。

## 主流程：想法 → 交付（idea → ship）

大多数工作都会经过这条路线：你有一个想法，并希望将其构建出来。

1. **`/grill-with-docs`**——通过访谈磨砺想法。当你**拥有代码库**时从这里开始：它是有状态的，会把获得的认知保存在 `CONTEXT.md` 和 ADR 中。（没有代码库？使用 `/grill-me`——参见“独立技能”。两者运行相同的 `/grilling` 原语；`grill-with-docs` 会留下书面记录。）
2. **分支——能否在对话中解决所有问题？**如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼查看的 UI），就绕道构建原型，并在两个方向上使用 **`/handoff`** 作为桥梁（参见“跨会话”）：
   - 使用 **`/handoff`** 导出上下文，然后基于该文件打开全新会话，
   - 使用 **`/prototype`** 通过一次性代码回答问题，
   - 再使用 **`/handoff`** 带回获得的认知，并在原始想法任务中引用。
3. **分支——这是跨多次会话的构建吗？**
   - **是** → 使用 **`/to-spec`**（把任务转换为规格），然后使用 **`/to-tickets`** 将其拆分为曳光弹工单（tracer-bullet tickets），每个工单声明自己的**阻塞边（blocking edges）**。在本地跟踪器中，每个工单是 `.scratch/<feature>/issues/` 下的一个文件，手工按阻塞项优先顺序处理；在真实跟踪器中，边会成为原生阻塞链接，因此阻塞项已经完成的任何工单都可以领取——为每个工单启动 **`/implement`**，并在工单之间**清空上下文**。
   - **否** → 就在当前上下文窗口中直接使用 **`/implement`**。

   无论走哪条分支，**`/implement`** 都会在内部驱动 **`/tdd`** 构建每项议题——每次一个红绿切片（red-green slice）——然后在提交前运行 **`/code-review`**，沿两个轴（Standards + Spec）审查差异。如果只是想在没有完整规格的情况下以测试优先（test-first）方式构建具体行为，就单独使用 **`/tdd`**；如果想依据固定点审查分支或 PR，就单独使用 **`/code-review`**。

### 上下文卫生（Context hygiene）

将步骤 1–3 保持在**一个不中断的上下文窗口**中——完成 `/to-tickets` 前不要压缩或清空——使追问、规格和工单都建立在同一套思考上。之后，每个 `/implement` 都从全新上下文开始，以工单为工作依据。

这一做法的限制是**[智能区（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能保持敏锐推理的窗口（在先进模型上约为 120k tokens）。如果会话在 `/to-tickets` 之前就接近该上限，不要在能力退化时继续推进——使用 `/handoff`，然后在全新任务中继续。

## 入口支线（On-ramps）

入口支线是产生工作的起始情境，随后会汇入主流程。

- **缺陷和请求不断堆积** → **`/triage`**。它让议题依次经过分诊角色（triage roles），生成智能体就绪议题（agent-ready issues），供 **`/implement`** 稍后领取。

  分诊只适用于**不是你创建的**议题——缺陷报告、传入的功能请求，以及任何未经处理的原始内容。`/to-tickets` 生成的工单已经达到智能体就绪状态，所以**不要对它们进行分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于棘手问题：第一眼看不出原因的缺陷、间歇性不稳定失败（flake）、在两个已知正确状态之间悄然引入的回退。在建立**紧密反馈循环（tight feedback loop）**之前，它拒绝空想理论——该循环是一条已经会在*这个*缺陷上变红的命令——随后用回归测试完成修复。如果复盘发现真正问题是没有良好接缝可以锁定缺陷，就交接给 **`/improve-codebase-architecture`**。

- **庞大而迷雾重重的工作——绿地项目或大型功能构建，无法在一次会话中容纳** → **`/wayfinder`**。当从当前位置到目的地的路径尚不可见时，它会在议题跟踪器上绘制由调查工单组成的**共享地图（shared map）**，再逐个解决这些工单——产出的是**决策，而非可交付物（decisions, not deliverables）**——直到迷雾退去、道路清晰。随后在 **`/to-spec`** 处汇入主流程（或者，如果工作最终足够小，就直接进入 **`/implement`**）。**`/grill-with-docs`** 用于磨砺能够在一次会话中掌握的想法，而 wayfinder 用于无法在一次会话中掌握的想法。

## 代码库健康（Codebase health）

这不是功能开发，而是维护。

- **`/improve-codebase-architecture`**——只要有空就运行，使代码库始终适合智能体操作。它会揭示**深化机会（deepening opportunities）**；选择其中一项就会_产生一个想法_，可在 `/grill-with-docs` 处带入主流程。它是发现候选项的勘测；下文的 **`/codebase-design`** 则是设计所选候选项的工作台。

## 底层词汇（Vocabulary underneath）

两个由模型调用、运行在其他技能*下方*的参考技能——每一个都是其词汇的单一事实来源（single source of truth）。当问题在于**用词**而非流程时直接使用；也可以让上层技能自行引入。

- **`/domain-modeling`**——磨砺项目的*领域*语言：质疑模糊术语、解决多义词（例如 “account” 同时承担三种含义）、将难以逆转的决策记录为 ADR。这是 `/grill-with-docs` 所驱动的主动实践，用于让 `CONTEXT.md` 保持为干净的词汇表。
- **`/codebase-design`**——用于设计模块*形态*的深模块词汇（模块 module、接口 interface、深度 depth、接缝 seam、适配器 adapter、杠杆效应 leverage、局部性 locality）：在清晰接缝上的小型接口后放置大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 跨会话（Crossing sessions）

- **`/handoff`**——当任务已满或需要分出支线（例如进入 `/prototype` 会话）时，它会把对话压缩成 Markdown 文件。不要在原地继续——应当**打开新会话并引用该文件**，把上下文带过去。它是在两个方向上连接上下文窗口的桥梁。当你需要**全新会话**但又必须**保留当前对话**时使用。
- **`/compact`**（内置）——留在**同一对话**中，让较早轮次得到摘要。在**阶段之间有意设置的中断点**使用，此时你不介意失去逐字历史。不要在阶段中途压缩——智能体可能迷失方向。`/handoff` 分叉；`/compact` 延续。

## 独立技能（Standalone）

完全位于主流程之外。

- **`/grill-me`**——与 `/grill-with-docs` 相同的毫不留情访谈，但适用于**没有代码库**的情况。它无状态：不会在本地保存任何内容，也不会创建 `CONTEXT.md`。用于磨砺任何不属于仓库的计划或设计。
- **`/prototype`**——用于回答一个设计问题的小型一次性程序：这个状态模型是否合理，或者这个 UI 应当是什么样子。从第一天起即可丢弃——保留答案，删除代码。它是主流程第 2 步中的绕行路径，但凡设计问题难以在纸面上确定，都可以使用。
- **`/research`**——将阅读工作委派给**后台智能体（background agent）**：它依据**一手来源（primary sources）**调查问题，然后在仓库中留下带引用的 Markdown 文件。它阅读时你可以继续工作。它产生的文件应当在 `/grill-with-docs` 处*带入*主流程——调研为思考提供材料，而不是取代思考。
- **`/teach`**——跨多次会话学习一个概念，并把当前目录作为有状态工作区。
- **`/writing-great-skills`**——关于如何良好编写和编辑技能的参考。

## 前置条件（Precondition）

**`/setup-matt-pocock-skills`**——在第一次运行工程流程前执行，用于配置其他技能所假定的议题跟踪器、分诊标签和文档布局。也支持自定义议题跟踪器。
